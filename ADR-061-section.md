## ADR-061 · Snapshot-style sources go increment per record: the write unit drops to the part (a message record carries its row only, parts are records of their own), readback assembles mixed whole-file and increment records by last-version-per-record with implicit and explicit tombstones, opencode first, and the usage criterion stays the relative ceiling with an estimation method — not a pinned number (2026-10-22 drafted; direction, sequencing and criteria Dim-approved 2026-10-20, 46 §0 / §5.1 A3 / §8.3; 正手 approved with mandatory edits 2026-10-22 — B1, B2 and all eight open-point rulings folded in)

### Context

1. **The measured problem: a snapshot source re-stores the whole session every pass.** [fact, 46 §2] One measured opencode session produced **150 shards in its life, each one line = the entire session, 13.3 → 16.0 MB, one copy every ~70 minutes**, while the session's own content grows only 1–5 % per hour. opencode is 6.5 GB of the 7.2 GB (90 %) written to the stage in a week (2135 shards); its collect leg is 1163 s of the 1283 s hourly collect; the same hour's remote `data_added` was only 33 MB after repo-side dedup + compression (~1/9 — the repo absorbs repeats, not growth). 46 §3's target 2 quantifies the gap: writes should ≈ new content; append-style sources already sit at ~1×, snapshot-style sources sit at **50–100×**. The worst case is our own usage: deputy sessions (oc-*) are opencode long sessions that stay open for days and get heartbeated hourly — 46 §2's 📌 wording. H4 is the same item — deferred 2026-10-13, measured 2026-10-20 at 6.5 GB/week, folded here (HUMAN-TODO H4 line).
2. **Where the behaviour lives, code-verified at `18e7a098`.** [fact] `collect.rs:1-10` — collection is read-only toward harness files; the opencode SQLite source keeps a *logical high-water cursor* (session `time_updated`, message/part row counts and greatest `(time_updated, id)` keys — `sqlite_probe.rs:2155-2208`), and **any mismatch resets the logical read to a complete session export, "deliberately preferring a measurable duplicate over a silent omission"**. `process_opencode` (`collect.rs:3335-3435`): cursor equal ⇒ skip; `read_opencode_session` (`sqlite_probe.rs:1383-1459`) returns **one JSON line** = envelope `chat-stasher.opencode.session.v1` = `{session, messages, orphan_parts}`; the ADR-024 content guard short of writing (`stage_holds_this_export` `collect.rs:510`, `export_content_matches` :2618) advances the cursor without a shard; a changed session writes one shard whose single line is the full session (`store.rs:2022-2030` allow-exact-repeat writer — cursor advancement is itself a validated new observation). **Every message row and every part row carries a stable id** (`message.id`, `part.id`, `part.message_id`; messages ordered `time_created, id`, parts `message_id, time_created, id`) — the precondition 46 §5.1 A3 asserts for snapshot sources holds for opencode as measured fact, and it holds at part granularity, not only per message. **The bulk of opencode bytes sits in parts (tool outputs, not message prose), and one agent round is one message carrying tens to hundreds of parts** [正手 2026-10-22, 必改 B1's own case].
3. **What a session's archived body is today.** [fact] `readback.rs:882-892` — the body handed to readers is **that snapshot's shards concatenated in global sequence order**, and the cumulative walk groups a session by its newest snapshot appearance (ADR-021). For a snapshot source that means the reader's "session body" is today N complete copies concatenated — exactly ADR-024's deferred note (point 1 of the draft Status). The proof/debt identity is a different thing: the raw-concat triple `(shard_count, concat_bytes, concat_sha256)` computed identically by the stage (`verify.rs:474-500`) and the archive (`readback` `ReadAllReport`), carried per destination with the two-way discharge rules (`collect.rs:36-64`, ADR-012/013: still-staged ⇒ owed; gone ⇒ the destination's archive must hold the exact triple; anything else is unverifiable ⇒ unread ⇒ full reread). This split — raw shard-set identity vs reader-facing body — is where this ADR does its work.
4. **The machinery this design reuses.** [fact] Shard sequence numbers are a persisted high-water mark written *before* the shard — never reused, reclaim-proof (ADR-020 Phase 2, `store.rs:1898-1966`). A per-row delivered set already ships for Grok Bot: `OffsetEntry.grok_bot_row_digests` = SHA-256 of each delivered row's canonical JSON, so an identical replay delivers nothing and a changed row delivers the new variant exactly once (W986, `collect.rs:136-141`, `process_grok_bot` :2102-2173) — row-level increment is not a new mechanism in this codebase, it is a precedent. The web extension delivers whole-conversation bundles whose identity is `platform.sessionId` + `file_sha256` and whose envelope the CLI stores verbatim (`contracts/inbox.schema.json:78-165`, W213 fingerprint) — snapshot-shaped at ingest, fingerprinted as a whole.
5. **The approved decode of "按消息增量", read one key finer.** [fact, 46 §5.1 A3, Dim 「都同意」 2026-10-20] 「collector 记住每条会话『已写出的消息 id → 内容哈希』，只把**新消息和被改过的消息**写成新记录；读取时按消息 id 取最后一版拼回整条会话」; the ✗-list is binding scope: the read side must assemble (拼), deletion upstream must leave a marker without deleting what we stored (「记一条删除标记，不删我们已存的」), and **old whole-file shards must mix-read with new increment records** (兼容已存量). The ⚠️ debate is already answered in-source: the id→hash map 「必须能从暂存区 / 归档里推出来…不是只存在游标里。丢了就退化成『整份再写一次』，和今天一样，不会丢数据」 — ADR-012's cursor-is-a-verifiable-cache applied to the map. [正手 2026-10-22, 必改 B1] The approved principle survives with the key made finer: last-version-per-id applied per **record** — message rows keyed by `message.id`, parts keyed by `part.id` — because the state the principle protects (a running agent round, one message with tens/hundreds of parts growing between passes) is exactly what message-level granularity rewrites wholesale. Non-goals (46 §3): no storage-backend change, no crypto/masterkey change, and the extension's *capture* method stays — only the shape it hands the stage may change. A2 (stage shard compression) is a “便宜的补充：如果实现成本低就一起做；否则放后面” (46 §5.1/§6) — a separable ticket, never the plan.

### Decision

**D0 — Scope line.** What changes: the *write* path of snapshot-style sources (opencode first) at **record** granularity (message row, part — B1), the cursor fields that cache the increment state, and the *reader-facing body projection* of sessions (an assembling view whose default is the source's final state, with deleted content reachable through a switch — B2). What never changes: the archive (append-only, destinations immutable — a never-rewrite guarantee that covers the existing 2135-shard stock, per-session with its 150-copy lives), the raw shard-set identity triple and both discharge rules, shard seq high-water semantics, session ids (`opencode.<machine>.<sid>` stays whole by ADR-057 R2), the extension's capture method, reclaim's proof question (ADR-060's territory), and every append-style source (claude-code / codex / file+jsonl offsets — already ~1× and untouched, ADR-011's offset path).

**D1 — The write unit becomes the source's own row: the part — and a message record carries its row, not its parts.** [正手 2026-10-22, 必改 B1] Per snapshot-source session the collector keeps the approved map **{record id → content hash}**: message rows entered under `message.id`, parts under `part.id`. A pass writes:
- **new message rows** — one record each: the message row itself, **without its parts inlined** (the v1 fold `read_opencode_session` performs stays a *read-side* composition; the record level does not repeat it);
- **new parts** — one record each under its own `part.id`;
- **changed content** — a changed **part** re-emits exactly that part's record (hash over that part's own bytes); a changed **message row** re-emits the message-row record; nothing else of the session is re-written for that edit. The session-level 50–100× becomes a **part-level worst case** and the pass-level write collapses to Σ(new+changed records) — an in-flight agent round costs only the records it actually grew;
- **deletion markers** — append-only tombstone records for messages/parts the source dropped; assembly drops them from the view, **stored bytes are never deleted by us** (invariant 3; the source deleting its row is the source's act). Tombstone word: `deleted`, shared by message and part records, with a `kind` field distinguishing them [正手 2026-10-22 裁定 1];
- **a session-observation record for the session's own row** — written only when that row's own bytes changed (`session.time_updated` changing changes it, so in practice: exactly the passes that observed change; a few hundred bytes when it fires) [正手 2026-10-22 裁定 4].
Unchanged records are never re-serialized into stage records; the unchanged-content guard (ADR-024 D3) stays as a second dedup layer beneath the map. The pass still *reads* the session in full (one SQLite transaction, one serialize-and-hash sweep) — the saving is on write bytes, not read bytes; unchanged sessions still skip for free behind the cursor fast path. Record shapes, decided [正手 2026-10-22 裁定 1]: **one record = one line**, plus the small session-observation line (the store's line rule, the W986 precedent, the activity parser); schema string **`chat-stasher.opencode.session.v2`**; the exact envelope field names are 待 SG 实现定. The fixed semantics: every record is self-describing (source, session id, record id + kind, per-record hash), sortable by the source's own ordering columns, and last-wins-mergeable with every other record — including v1 whole-file lines, which are records carrying **all** of a session's messages at one observation point (and, per D3, the absences of that observation too). Orphan parts are just part records whose message row the source never wrote — they key under their own `part.id` on the same path as every other part record [正手 2026-10-22 裁定 6: naturally holds after B1 — no third path].

**D2 — The map lives in the stage, cached in the cursor (ADR-012 applied).** The per-session id→hash map must be **derivable from the session's shard set alone** (D1's self-describing records make each shard's contribution computable; reading the set rebuilds the map), because the map is a cache over what was *written*, and ADR-012 forbids trusting a cursor against the truth it claims to copy. The state-file entry caches it — shape decided [正手 2026-10-22 裁定 2]: a **per-record digest list** (the W986 `grok_bot_row_digests` shape: one digest per entry); once a session's list passes **5000 entries**, the entry stores an overall map digest instead and the map is rebuilt from the staged records on mismatch. Discharge reuses today's two ways unchanged: shards still staged ⇒ the debt (and the map behind it) is accounted; shards gone ⇒ the destination's archive held the exact triple ⇒ the debt was settled and the map stays consultable. Map unknown/absent/None ⇒ **never "no new messages"** — unknown is not empty (invariant 1): the session re-exports in full once, which re-derives the map, and incremental writing resumes. That single full export is today's behaviour exactly — 46 §5.1 ⚠️:「丢了就退化成『整份再写一次』，和今天一样，不会丢数据」— **and it is itself a complete observation, so D3's implicit-tombstone rule applies to it: the degrade path keeps the default view byte-faithful instead of losing deletions** [corollary of 必改 B2].

**D3 — Readback assembles last-version-per-record, across all shards the archive holds, whole-file and increment records mixed — with tombstone semantics, so the default view is the source's final state.** [必改 B1 拼装 + 必改 B2] For every session regardless of era:
- enumerate every shard of the session found in the cumulative snapshot walk (the machinery `readback.rs:807`'s walk already enumerates all snapshots);
- merge per **record id** (message row / part): the newest record wins by global shard sequence — a v1 whole-file line contributes all its messages at its observation point, an increment record contributes its own;
- **one whole-file record = one complete observation** [正手 2026-10-22, 必改 B2]: a message/part *known from the session's earlier records* that does not appear in it is, in the view, treated as deleted as of that observation — an **implicit tombstone**. The increment era sends **explicit tombstones** for its deletions (D1). A delete-free session reduces to exactly the pre-review merge; a deleting session — and opencode deletes: revert, compaction — stays correct instead of resurrecting what the source removed (the pre-review reading is recorded under Rejected);
- parts hang back onto their owning message by the source's own columns `message_id, time_created, id`; the surviving messages order by the **source's own rule** (opencode: `time_created, id`), recomputed at assembly — never by arrival order; orphan parts merge by the same rule under their own ids [必改 B1: 拼装时 part 按 `message_id, time_created, id` 挂回各自的 message; 裁定 6];
- tombstones (implicit and explicit) remove their record from the view **without removing anything from storage**; a re-observed previously-tombstoned record is a resurrection — data, not an error (D4).
**Byte-identity contract (given teeth, and now including sources that delete):** at quiescence (source stopped changing, all observations staged) **the assembled default view equals a fresh `read_opencode_session` export of the source's final state** — the same serializer's bytes, not a second canonicalization format [正手 2026-10-22 裁定 3]; equality is required **at quiescence only** (mid-growth enforced-equality is out of scope). This is §4.7's 「读回逐字节等于最后一版」 given teeth, and it is a state today's reader cannot reach at all: its body is N complete copies concatenated (Context 3, ADR-024's deferral), which equals no single version of anything. The existing stock needs **no conversion ever** (append-only holds for the stage as for the archive): assembly reads v1 whole-file lines as ordinary all-messages records — for a delete-free legacy session the view is the newest single copy (a reader-visible change vs. today's N-copy concatenation, exercised by D7's mixed-stock fixture, touching no stored byte); for a legacy session along whose life the source deleted, the view is the source's state at the newest observation — correct, where today's concatenation and the pre-review merge both mislead. The cross-snapshot reach stays load-bearing for the reclaim case: after a reclaim deletes a session's stage set (debt settled, D2), the session's next change writes increment shards alone; a per-snapshot assembly would read a one-record "session". Per-record assembly across the whole archived set is the correct rule, and it is also why **the raw triple stays the only proof**: L3, reclaim, `dump_machine_sessions` (which keeps shards separate), and dest-init copying all keep their exact current, raw-concat semantics; the raw-concat/assembly parity survives only where a snapshot-source session holds a single shard — for multi-copy or increment-era sessions the two diverge by design (Invalidates 2).
**Deleted content is never lost and stays reachable — the product point 「工具删了自己的历史，我们还留着」** [正手 2026-10-22, 必改 B2]: everything the source deleted remains stored byte-for-byte in the shard set (invariant 3). `read` / `export` gain a switch (working name `--include-deleted`; exact flag spelling 待 SG 实现定) that emits the deleted messages and parts **at their original positions with deletion markers**; the UI can present them expanded (form 待 SG 实现定). The default view stays the source's final state; the switch is how the deleted history is reached — correcting the view can never hide the archive's extra retention.

**D4 — Correctness criteria (去重 / 顺序 / 补漏), each falsifiable.**
- **去重:** a record whose (id → hash) equals the map entry is never written; an identical replay of the same observation delivers nothing; a changed record is written exactly once (new hash) — the W986 convergence rule lifted from rows to records. Cursor advanced + bytes identical still counts as a new observation (the `store.rs:2022` allow-exact-repeat rule) but writes nothing new — zero-cost, kept.
- **顺序:** assembly ordering comes from the source's ordering columns carried on every record; a re-emitted record replaces its own slot; no consumer can observe arrival order.
- **补漏:** every conflict resolves toward *more data*: cursor field mismatch ⇒ full export (today's rule, verbatim); map unknown ⇒ full export; a source record missing from our map ⇒ written (the map records what we wrote, not what the source asserts we have); a re-observed previously-tombstoned record ⇒ written anew (the tombstone stays, newest wins — a resurrection is data, not an error). **Absence is evidence of deletion only inside a complete observation** (D3's whole-file rule, B2); an id absent from the map is *unknown*, never assumed deleted — unknown-never-empty applies to every new field (invariant 1).
- **Inherited invariants:** unknown-never-empty on every new field; a session that cannot be *fully assembled* is an exit-3 read failure, never a short count (invariant 2); append-only — tombstones mask, never erase (invariant 3); measurable duplicate over silent omission, everywhere (collect.rs's founding rule — a whole-file observation is the one shape where "not present" is itself measured information, and it is worded as deletion, never as silence).

**D5 — Sequencing and family: opencode first; the extension and Grok Bot follow as tickets in the same family.** opencode is the 90 % and the only measured heavy source, so SG-3's first ship is opencode-only; negligible-class machines need not schedule anything (46 §2). The follow-ons inherit D1–D4 as already-built machinery: the extension's whole-body bundles convert at **ingest** (capture method untouched, 46 §3 non-goal) by the same per-record map — its payloads carry platform message identities, and W213's bundle-level fingerprint continues to guard whole-bundle integrity alongside; Grok Bot already *is* row-incremental (W986) — its follow-on is alignment (same map abstraction, same assembly path, envelope family), not a new mechanism. All sources' v2 stamps (source-specific schema strings like `chat-stasher.opencode.session.v2`) share **one assembly code path** [正手 2026-10-22 裁定 7], so the follow-on tickets are naming + ingest, not re-design. A2 compression is a freestanding cheap ticket (46 §5.1's "if cheap"), kept **off SG-3's first-ship critical path** [正手 2026-10-22 裁定 8]; claude-code/codex/append sources are declared out of scope *because* they already satisfy the ceiling.

**D6 — Usage criterion: the relative ceiling is the target; the absolute number is produced by a method, not pinned (「给估算方法不拍数」).** The committed criterion is 46 §4.2's own sentence: **opencode hourly writes ≤ 1.2 × the session's actual growth in that hour** — edge semantics decided [正手 2026-10-22 裁定 5]: the ceiling aggregates **hourly** with a lower bound of **`max(1.2 × growth, 64 KiB)`** per hour (a metadata-only pass stays inside the ceiling), and the **day-level gate compares the sum of the 24 hourly values against the day's total** (both sides in written bytes, the same clock); read on the same one-week window as §4.2's 暂存区净增长 ≤ 1 GB line (which SG-2 and this ADR jointly produce), plus §4.7's fixture form (stage bytes ≈ final size × 1.x after 20 growth steps). The estimation **method** for the absolute question ("6.5 GB/week down to what?"):
1. during any pass the collector already serializes the full export to hash per record — so per pass it knows, without new I/O, the measured **true growth** `Δ` (new + changed bytes since last observation) and the measured **written bytes** `w` (Σ increment records, session-observation record included);
2. observed amplification `A = w / Δ`; the committed shape is written ≤ `max(1.2 × Δ, 64 KiB)` per hour;
3. weekly opencode write projection = `Σ` of the gate's measured per-pass true growth × 7 × ≤1.2 — reported as a **band from measurement**, never a promise.
As a sanity cross-check only [inference, explicitly not a target]: today's stage amplification for snapshot sources is 50–100× (46 §3.2), so 6.5 GB/week ÷ 50–100 × 1.2 lands in the ~10² MB/week class — two orders of magnitude down, consistent with 46 §5.4's collect-time expectation (「opencode 的 collect 从 19 分钟降到秒级」). The remote side follows the same direction: repo-side dedup repeats but not growth (46 §2's 🔁 note), so `data_added` shrinks toward compressed-true-growth [inference]. The first real numbers come from the live-day gate (D7) — this ADR deliberately pins no absolute figure anywhere.

**D7 — Acceptance (46 §4.7's second half + §6's live gate; the boundary ADR-060 D8 wrote for this ADR).** Fixtures, red-proven first:
- one snapshot-source session grown 20× ⇒ stage bytes ≈ final size × 1.x; **readback (assembled) byte-identical to the last version** (§4.7 verbatim; quiescence-only equality, same serializer's bytes [裁定 3]);
- **the B2 fixture** [正手 2026-10-22, 必改 B2 的夹具]: a session observed as **whole-file v1 → the source revert-removes two messages → the session grows again** ⇒ the default assembled view is **byte-identical to the source's final export**; with the deleted-content switch on, those two messages appear at their original positions, marked deleted;
- **part-level write (B1):** a pass that changes only one part re-emits exactly that part's record (the message-row record is not re-written); a new message arriving with N parts writes 1 + N records;
- identical replay delivers nothing (convergence); a tombstone masks without erasing; a post-tombstone resurrection delivers;
- **mixed stock**: a pre-era whole-file session that then grows incrementally assembles correctly from both kinds (兼容已存量), with no conversion of the old shards;
- post-reclaim reappearance: increment-only shards in a newer snapshot assemble across snapshots to the full body (D3's hard case);
- cursor/map loss ⇒ exactly one full export, then incremental again (degrade-to-today — and that full export behaves as a complete observation, so the view stays correct through the degrade);
- L3 stays green on raw triples throughout; seq monotone throughout; assembly failure exit-3 covered;
- the live gate (46 §6): a real deputy session runs one day on m1max — written ≤ 1.2× measured growth (D6's hourly rule + floor), assembled readback byte-identical to the source's final export; the gate also reports D6's first measured band.
No shipping dependency on SG-2/ADR-060 (reclaim shrinks what exists; this stops producing it — independently landable, measured on the same one-week §4.2 window), and no LM/ADR-062 coupling (mirror sync and its reclaim precondition are snapshot-set facts; cross-snapshot assembly cost on mirror-first reads is revisit trigger 6).

### Consequences

- Snapshot-source writes ≈ true growth at record granularity: the stage stops paying 50–100×, opencode collect time drops toward seconds [inference, per 46 §5.4], and the remote stops receiving repeat bodies wholesale — the one-hour sample wrote 287 MB locally while the repo side recorded only 73 MB `data_added` (33 MB packed), i.e. the repo was already telling us how much was repeat; the increment writes the non-repeat part directly [inference].
- The read side gains one shared, source-generic assembly function — legacy whole-file stock, mixed-era sessions, and increment-era sessions all flow through the same last-wins-per-record projection; no session is ever rewritten or "converted" (append-only holds for the stock as much as for the archive).
- **The deleted history becomes a product surface instead of a correction loss**: a source that reverts or compacts away its own past (opencode) keeps those turns archived and reachable in place via the read/export switch, while the default view stays byte-faithful to the source's final state — 「工具删了自己的历史，我们还留着」 lands as a property, not a loophole (B2).
- Line-oriented consumers (activity index parser `activity.rs:1353+`, FTS, export, view/UI) must fold increment records by record id and carry deletion markers, or increment-era sessions over/under-count — the fold is part of the implementation ticket, and SG-4's re-measure (index rebuild is already its own scheduled item) re-baselines with it.
- Per-pass cost model changes shape, not just size: changed sessions still pay one full SQLite read + serialize (cheap, in-memory); unchanged sessions skip (cursor fast path, unchanged); stage write + fsync + push-scan volume collapse; the session-observation record fires only on changed passes (adjudicated cadence).
- New honest failure mode: a session whose shard set across *all* archived snapshots cannot be assembled (an increment gap: e.g. a shard lost to a bug) reads as an exit-3 named failure — loud, never silently shortened. The map cache stays bounded: per-record digest list up to 5000 entries, then overall digest + stage-side rebuild (D2).
- Users' existing heavy sessions keep their archived history byte-for-byte; new growth of those same sessions arrives as increments — the mixed read is permanent furniture, as H4's fold intended; the doc duty (`docs/sources/opencode.md`, how-it-works readback paragraph, changelog) lands with the implementation in one change (ADR-058 D6 precedent), no earlier.

### 🔴 Invalidates (必填)

1. **Assumption down: "an archived session's reader body is one snapshot's shards concatenated"** — `readback.rs:882-892`'s doc and the ADR-021 cumulative walk's grouping rule (body = the newest snapshot appearance's set). **Dependents named:** every consumer of the body callback (`export`/`view`/UI readers of `for_each_archived_session` `readback.rs:910-917`), the `activity.rs` line-parsers fed from stage shards, and ADR-021's own Consequences wording. **Replacement:** per-record newest-wins across the entire cumulative walk, with the tombstone semantics of D3 — for whole-file-era sessions this yields the source's state at the newest observation (the newest single copy for delete-free sessions; a deletion-correct final state otherwise), deliberately replacing the N-concatenated-copies body ADR-024 flagged and deferred to exactly this ADR; a reader-visible body change for legacy multi-copy sessions, testable, touching no stored byte. Append-style sources (claude-code/codex/jsonl) are outside this invalidation: their body stays raw concat, which for them already *is* the growth-log semantics and stays byte-identical. Note for the review: `verify` L3, reclaim proof, `dump_machine_sessions` (`readback.rs:824-880` — shards kept separate deliberately) and dest-init copying are *not* invalidated: they operate on the raw shard set, untouched by D3.
2. **Assumption down: "the body a reader gets is byte-for-byte what the L3 hash covers"** — the parity claim in `readback.rs:889-892` ("byte for byte the rule `BackupStore::read_cumulative_sessions` hashes by"). After this ADR the two stay byte-equal only for a single-shard snapshot session or an append-style session; for legacy multi-copy and increment-era sessions the raw triple remains the *proof* and the assembled body is the *projection*, and they differ by design. **Dependents:** any code or doc that reuses one digest for both jobs must now name which — this ADR is the record that splits them.
3. **Deferral resolved:** ADR-024's 「不在本条」 — "opencode re-exports a full snapshot per change; long sessions are concatenations of complete copies; separate ADR." This ADR is that successor. **Dependents:** ADR-024's Consequences wording (still true of the *old* era and of the degraded fallback path), and any prose elsewhere that repeats the concatenation-of-copies shape as permanent. ADR-024's content guard itself is explicitly *kept* (second dedup layer, D1).
4. **Assumption down: "a snapshot session's next change costs a full copy"** — the cost model behind 46 §5.4's timing math and the ~7 GB/week expectation. **Dependents:** SG-4's re-measure (already scheduled; re-baselines after this), H4's measurement framing (closed), and the §4.2 one-week acceptance arithmetic. **Replacement:** per-pass cost = full-read (bounded by session size) + write ≈ true growth ≤ 1.2× at record granularity.
5. **Not invalidated — re-affirmed for the review's perimeter:** append-only archive and the never-rewrite stock (invariant 3); ids `opencode.<machine>.<sid>` (ADR-002; ADR-057 R2 — unattributable store, id stays whole, surface rides 4D); ADR-012 (map = verifiable cache; unverifiable ⇒ unread ⇒ full export — the degrade path *is* the old behaviour); ADR-020 Phase 2 (increments take fresh seqs; counter written before shard; never reused); ADR-021's cumulative *verify* semantics (a reclaimed session is re-checked at the snapshot holding it — raw triples, unchanged); ADR-022 (push change detection sees the new shards; empty-stage gate unchanged); W986 Grok delivered-set semantics (extension of principle, not replacement); the extension contract @1/@2 and W213 (whole-body delivery and bundle fingerprint unchanged); ADR-060's healthy-set reclaim (orthogonal planes: reclaim shrinks, SG-3 stops producing); exit-code semantics 3/1/2 (assembly failure stays a read failure, exit 3); **46 §5.1 A3's own read-side principle (「按消息 id 取最后一版」) is re-affirmed, not superseded — B1 only makes its key finer** (message row / part).

### Rejected (recorded)

- **A1 — write-on, reclaim-mops-up:** treats the symptom in the one place it hurts least; the remote still ingests ~5.5 GB/week-equivalent repeats, the pre-reclaim week still eats ~7 GB, collect still spends its 19 minutes (46 §5.1 A1's own ✗ row).
- **A2 as the main plan (shard compression):** shrinks the factor, keeps the shape — 100× becomes ~15× at text-JSON ratios, collect time and stage *graph* untouched (46 §5.1 ✓/✗ verdict: “适合当补充，不当主方案”). Kept as a freestanding cheap add-on ticket only [裁定 8].
- **A4 — binary delta chains (xdelta/rsync-style):** format-independent but chain-shaped: one broken link poisons the tail, and per-record independence is exactly what "归档才是真相、每条记录独立可验" buys (46 §5.1 A4's own ✗; ADR-012's family rule).
- **Message-granularity records with parts inlined — the pre-review draft's own write unit [正手 2026-10-22, 必改 B1]:** opencode's bulk sits in parts (tool outputs), and one agent round is one message carrying tens to hundreds of parts; at message granularity a session that is *mid-round* — where deputy sessions live almost continuously — rewrites the whole in-flight message on every pass, so the gain collapses exactly on the workload this ADR targets. The fine-grained keys already exist natively (stable `part.id`, part sort columns, `part.message_id`; Context 2), and 46 §5.1 A3's principle survives unchanged at the finer key. The unit drops to the part.
- **Merge without deletion semantics — the pre-review draft's own assembly reading [正手 2026-10-22, 必改 B2]:** per-message last-wins alone reconstructs the source's final state *only if the source never deletes messages*; opencode has revert and compaction, so deleted messages would stay in the assembled view forever with no tombstone, the default view would contradict the source's final state, and the byte contract of D3 would be false in the exact cases it exists for. Replacement: whole-file records = complete observations (implicit tombstones) + explicit tombstones in the increment era (D1/D3), with the deleted content preserved and reachable (D3's last bullet).
- **Mass-converting the existing stock** (rewriting old session dirs to increments outside capture): violates append-only, re-runs the very amplification it removes, and buys nothing — D3's assembly reduces correctly without conversion.
- **Per-snapshot-only assembly** (avoiding the cross-snapshot merge): breaks exactly the post-reclaim increment reappearance case (D3); would force the old full-copy write precisely to keep reads simple — the thing SG-3 exists to remove.
- **State-only map** (never derivable from the stage): the ADR-012 violation 46 §5.1 ⚠️ already rejects; a lost map must degrade to a full export, never to silence-and-trust.
- **Byte-offset increments for the SQLite source** (ADR-011's file trick ported wholesale): a DB has no stable byte prefix to hash; the record id is the honest analogue of the offset — ADR-011's *principle* (read-only, ≈1×, prefix-hash fallback) transfers, its mechanism does not.
- **An opencode-only special case in readback:** the assembly must be the generic snapshot-source projection so the extension/Grok follow-ons and the mixed-era stock inherit one implementation, not three.

### Revisit triggers

1. opencode schema migration (session/message/part tables, id semantics, or ordering columns change) ⇒ cursor fields, envelope and assembly order re-verified; failure is loud, never a silent empty map.
2. Observed amplification exceeds 1.2× on real deputy weeks ⇒ re-open the overhead budget: record envelope fat, per-pass session-row cadence, batching — and the 64 KiB floor's adequacy alongside them.
3. Cross-snapshot assembly cost measurably surfaces on read paths (rare-path, cached-archive) ⇒ re-balance with a stage-side assembled-body cache that is never used as proof — ADR-020 Phase 3's summaries-trick applied twice.
4. The extension/Grok follow-on specs reveal a payload the per-record shape cannot express (their bodies/part shapes) ⇒ re-open D1's record shape (D5's family claim).
5. Activity/FTS/export folds drift from source counts on increment-era sessions ⇒ re-open the fold design jointly with SG-4's index re-measure.
6. LM-3 (read-local-first, ADR-062 family) wants assembled-body equality enforced on the mirror ⇒ re-check the raw-triple vs assembled-body split (D3) before mirror reads ship.
7. The tiny-metadata edge (a session-row-only update technically busting the hourly ceiling on a near-zero-growth hour) proves user-visible ⇒ re-open the floor value (`max(1.2 × growth, 64 KiB)` per 裁定 5 — the floor exists so it does not fire; if it still hurts, the number is what re-opens).
