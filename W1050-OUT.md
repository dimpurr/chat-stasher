# W1050 OUT — READ-RACE A→C implemented, B not built

## Scope, as landed

- **A — reload once, re-read once.** The READ-RACE gate is a product seam in
  `crates/chat-stasher/src/readback.rs`: when a read-back's attempt fails with
  an index-miss (a snapshot tree or shard blob the *loaded* index does not
  hold), the read waits the v3 gate's bound (one retry, 300 s cap), then
  re-runs its whole attempt once; every attempt re-opens the repository, so
  the re-run **is** the "从归档闭包重载一次索引" reload — index files are
  re-read from the repository before it judges the same snapshots again.
- **C — otherwise keep UNKNOWN, exactly as before.** A still-missing tree
  keeps the established semantics untouched: `Err` + the walk's own
  `UNKNOWN:` wording (exit 3 at the CLI) for the strict readers, a warning +
  an incomplete report for the cumulative ones, plus one added context line
  saying the product gate already spent its one retry (so an ops driver
  knows its own sleep+retry composes with, not duplicates, the in-product
  gate). The proof-of-absence wording (`holds no shards … all of them were
  read`) stays reserved for a walk that read every snapshot and found
  nothing; `rc=3`'s meaning is unchanged anywhere.
- **B — nothing.** No older-snapshot fallback, no override switch, no knob
  that could mask a genuinely broken archive; the retry re-reads the same
  snapshots of the same newest-first walk.
- **f3a2cf58's origin: not investigated**, per the task.

## Where the gate sits (and where it deliberately does not)

Classifier: the pinned vendored reader attaches error codes to its three
index-miss sites — `I001` (blob lookup, `index.rs`), `I002` (tree lookup,
`blob/tree.rs` — the exact "Tree ID … not found in index" the 10-28 stop
showed), `I003` (data-blob dump, `commands/dump.rs`) — and the product
classifies through `rustic_core::RusticError::is_code`, structurally, down
the whole `anyhow` chain (the root survives as a `Box<RusticError>`; the
unit test pins that mechanics, and a backend error / plain bail / the C002
password error all stay outside the gate).

Wrapped readers (attempt re-run once on a classified miss):
- store.rs `read_session_concat_with_view` — `read --session`, the v2/v3
  drivers' exact path (the 10-28 evidence);
- store.rs `read_selected_sessions_with_view` — the `export` batch, same
  `dump_cumulative_session` walk;
- readback.rs `read_cumulative_sessions_inner` — `read --all-machines`,
  `verify` L3, the debt/duplicate walks;
- readback.rs `read_latest_per_machine` — the reclaim proof;
- readback.rs `for_each_archived_session_shards_with_policy` — the
  activity-index/FTS archive walks;
- readback.rs `dump_machine_sessions` — the ADR-013 shard restore.

Report-shaped readers return their attempt plus a raced flag (the warning
sites classify the raw rustic error), so the gate is symmetric over the
`Err` and the warning vocabulary, and a flagged first attempt retries on
the same budget as a classified `Err`.

**Not covered, on purpose** (each keeps today's behavior unchanged): search's
own metadata walk already records an unreadable snapshot in its
`unreadable` vocabulary and exits "did not finish"; the archive sidecar
readers (`read_archived_writers`, provenance) are single-file lookups off the
newest snapshot; `raw_export` walks export objects, not session shards. None
of these are the path the READ-RACE evidence was about; widening is a small
follow-up if the race ever bites there.

## Incident during the run — shared CARGO_TARGET_DIR aliased across worktrees (worth Dim's attention)

Mid-run the integration test went from green to red with no source change:
the CI child's errors printed `error_code: None`, i.e. the spawned binary
linked a `rustic_core` rlib built from an **unpatched** vendor. Cause: the
sibling W1050-era worktree (W1049's lane, same base commit, same unpatched
vendor) builds into the same shared `CARGO_TARGET_DIR` (as the disk-incident
rules require) and the `rustic_core-<hash>` unit id is identical for both
checkout trees — whichever tree compiles that unit last wins the shared
artifact, and the other worktree silently links it without a rebuild. It
flipped my binary at 09:15; a `cargo clean -p rustic_core` plus rebuild from
this tree restored it and everything re-ran green afterwards. Two practical
notes:

- I did **not** change `CARGO_TARGET_DIR` (worker rule 1); the exposure is
  only while two sibling worktrees with a patched/unpatched same package
  both build into it, and it self-heals with a `cargo clean -p <pkg>` + rebuild.
- The new integration test doubles as a canary for this exact hazard: a
  clobbered build fails its `[read-back]` assertion loudly instead of
  passing vacuously. If W1049 lands without vendor edits, the aliasing dies
  with this branch's merge; if two workers ever concurrently patch the same
  vendored file, serialize their full-gate runs.
