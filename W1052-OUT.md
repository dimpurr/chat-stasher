## 2. "Where does the report line go" (ruling question)

**stdout, with per-line flush — proven from the repro.** The five diagnostic lines were already on disk (276 B) while the process was wedged (capture at +22 s), stderr held only the two r2 env warnings — `println!`'s LineWriter flushes every line even piped. The `concat len/sha256` line prints on stdout after the walk returns; it appeared the moment a window (1800 s) was long enough for the read to finish, and matched the stored sha. Nothing is buffered elsewhere; no second sink exists. Also: LM5-READSEM's "completed exit-0 run hashed fe3c…" claim is falsified — no code path exits 0 without printing the report; that capture was another early kill. The report-line fix needed was the unbounding and the naming above, not a plumbing change.

- Deadline workers read through `BackupStore::owned_twin()` (store.rs): Arc-cloned handles so the read's body-cache/mirror counters still reach the report, while a detached worker can't take the run's own store hostage. Bounded ssh reap (`reap_read_remote`) only fires when there is an endpoint; on its timeout the answer stands and the exit code is unchanged (masters stay open, said so).
